# 超級管理員管理能力：檢查與設計

日期：2026-10-08。狀態：依使用者確認的「先把本地版本設計好，再推送」範圍，本地管理功能與驗證完成。正式發布另行處理。操作範圍見 `super-admin-local-guide-2026-10-08.md`；發布說明見 `super-admin-release-2026-10-08.md`。

## 目標與完成標準

所有超級管理員都能從後台完成網站的營運管理，包括目前需要直接操作資料庫的新增助教、轉班及批量考勤修正。相同角色有相同權限，不因是否為站主本人或某個指定信箱而有差異。

這裡的「全部事務」是網站營運資料與權限管理；部署憑證、資料庫金鑰、原始碼發布不是後台帳號權限。保留既有發布流程。不得把 service-role 金鑰送到瀏覽器。

不能以隱藏按鈕代替伺服器授權。新操作必須能顯示影響範圍、提供明確成功／失敗結果，並留下操作人、時間、原因與原資料。批量更正與轉班要避免部分寫入造成資料不一致。

## 已核實的現況

- 正式資料庫目前有 4 個 `profiles.role = admin` 帳號。此處不複製個人信箱。沒有獨立的 `super_admin` 資料庫角色；後台標示的「超級管理員」就是 `admin`。
- `lib/admin-auth.ts` 支援角色、環境變數信箱、資料庫 allowlist 三種來源。將 allowlist 設為 inactive 不會自動移除既有 admin 角色；帳號授權與撤權必須一起設計。
- `app/api/admin/route.ts` 已提供季度、課程、教練登記、訂單、付款帳戶、商品和網站內容管理，不能重做成另一套互相衝突的後台。
- 教練登記介面只能選既有教練身份；新的姓名和信箱沒有完整新增入口。底層公開資料 upsert 雖可建資料，但沒有串接成一般管理流程。
- 教練到課介面有單筆人工更正，沒有批量更正。`app/api/admin/coach-duty/route.ts` 的 `archivedSeasonResponse` import 原本位於檔案末尾；初步閱讀誤以為缺少，完整型別檢查後已更正結論，不列為原有故障。
- 查無正式的學員轉班 API／介面。之前曾喜煌轉班需要直接改 `signup_leads`；正式功能須同時處理點名資料、帳務及資格，而不是只改顯示名稱。
- `lib/finance-access.ts` 的財務密碼管理仍取決於 `FINANCE_MANAGER_EMAILS` 或第一個 `ADMIN_EMAILS`。本機這兩個設定目前皆空；不能據此宣稱正式部署沒有信箱限制。角色與指定信箱交叉判斷本身不符合相同超級管理員權限的目標。
- 已封存季度的寫入保護存在，但既有狀態選擇器和 API 都禁止解除封存。第一輪只看狀態清單時誤判可恢復；收尾追查介面 disabled 條件與共用寫入保護後更正。需要明確的解除封存操作，避免背景同步改寫歷史。

## 實作順序

1. 驗收現有管理入口，統一財務設定授權，補上新增教練／助教的完整操作。
2. 補教練考勤批量更正與學員轉班（伺服器驗證、交易、審計、預覽及 UI）。
3. 補帳號授權／撤權及診斷能力，逐項驗證現有營運管理入口的角色一致性。
4. 執行 API／資料庫／瀏覽器驗收，整理可發布版本；經既有發布授權後套用遷移並驗證正式站。

## 第三輪：帳號授權、撤權與診斷（本地，未發布）

- 新增 `20261008120000_admin_access_management.sql`：`resolve_account_role` 從 Auth 真實信箱與驗證狀態判定權限；`admin_set_access` 將授權來源、帳號角色與審計記錄在同一交易內變更。資料庫明確撤權優先於環境白名單與既有 admin 角色。
- 撤權同時記錄帳號 ID，因此更換信箱也不會讓舊授權恢復。保留已啟用的教練身份，否則回到學員角色；保留原有業務資料。不允許自己撤權，並檢查至少保留一位有效管理員。
- 所有授權與撤權共用資料庫交易鎖，避免角色解析和撤權互相覆蓋。資料庫觸發器另外阻止舊版伺服器直接重新寫回已撤銷的 admin 角色。未驗證的新註冊帳號不會在註冊觸發器中取得 admin。
- `getAdminProfile` 和 `/api/account/me` 使用同一角色解析函式；解析失敗時不採用舊角色或環境白名單作備援。已有的 inactive 管理員資料會在遷移時即時降權。
- 新增 `/api/admin/accounts` 與共用 `AdminAccountManager`，電腦導航及手機「更多」都有入口。可按信箱查詢、授予與撤銷管理權限；原因必填，操作後重新讀取角色；可查看最近 30 筆授權操作。
- 診斷透過唯讀 `admin_account_overview` 查詢目標：未註冊／未驗證、角色、教練登記及 owner 關聯、目前班級、最近 10 筆裝置活動。診斷本身不啟用教練、不中斷目標會話，也不回傳登入憑證。裝置活動不能當作成功開啟工作台的證據。
- `scripts/verify-admin-access.mjs` 在 PGlite 通過：不同管理員等權、教練／學員拒絕、未驗證啟用限制、本人撤權拒絕、環境白名單／換信箱／舊會話不能繞過撤權、歷史 inactive 資料修正、直接角色回寫拒絕、審計失敗全部回滾、重複 Auth 信箱及缺少 profile 的拒絕、診斷唯讀、瀏覽器角色無 RPC 執行權。
- 應用測試 **266 / 266** 通過，包含新增 API 與角色解析測試。TypeScript、修改檔案 ESLint、繁體檢查通過；隔離 production build 成功產生 64 頁。

## 第四輪：學員資料、內部備註與完整列表（本地，未發布）

- 原學員後台只有查詢入口，手機「備註」明確顯示不能儲存。新增共用 `AdminStudentEditor`、`/api/admin/student-details` 及 `20261008130000_admin_student_details.sql`，可修改網站帳號姓名、電話、最佳成績、跑步目標及管理員內部備註。電腦名單點姓名／編輯按鈕進入，手機在詳情「資料與備註」進入。
